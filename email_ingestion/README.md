# Automated Underwriting Submission Intake

This repository implements an end-to-end prototype for the ingestion, document aggregation, and structured data extraction of unstructured broker emails and policy schedules. The sample emails are synthetic and strictly for the demonstration of the prototype. The pipeline combines a zero-shot Large Language Model (LLM) for entity extraction, with deterministic Python heuristics, to evaluate cross-document contradictions and trigger human-in-the-loop triage.

## 2. Prerequisites

* **Dependencies:** `pandas`, `groq`, `python-dotenv`, `jupyter`. 

## 3. End-to-End Execution Guide

Follow these steps to replicate the pipeline and evaluate the model from a clean environment.

### Step 1: Environment Setup
Clone the repository, navigate to the project directory, and initialise a virtual environment.
```bash
git clone https://github.com/Beck40/Gen-AI.git
cd Gen-AI/code/email_ingestion
python -m venv venv
source venv/bin/activate  # On Windows use: venv\Scripts\activate
pip install -r requirements.txt
```

### Step 2: API Configuration
Create a `.env` file in the `code/email_ingestion` directory and add your Groq API key:
```.env
GROQ_API_KEY=gsk_your_api_key_here
```
*(Note: If you skip this step, `02_email_ingestion.ipynb` will securely prompt you for the key at runtime).*

### Step 3: Exploratory Data Analysis (Optional)
Run `notebooks/01_exploratory_analysis.ipynb` to execute the EDA phase. This groups the flat markdown files by submission ID and calculates token volume to confirm all payloads fit comfortably within standard LLM context windows, bypassing the need for RAG or chunking.

### Step 4: Data Extraction & Triage
Run `notebooks/02_email_ingestion.ipynb`. 
1. The notebook parses the 50 underwriting submission and groups corresponding emails and attachments.
2. It passes each combined payload to the Groq LLM API (`temperature=0.0`) to extract the schema into a JSON object.
3. The raw text is passed through the `apply_confidence_rules()` function. This logic scans for material underwriting conflicts (e.g., "estimated" vs. "audited", or "standalone" vs. "group"), before the LLM can identify it's corrections, which results in "high" confidence.
4. The script exports the final extracted dataset to `../../data/email_ingestion/llm_extracted_submissions.csv` and any selected edge cases to `llm_extracted_submissions_edge_cases.csv`.

*To process the full dataset, ensure the `TEST_SUBMISSION_IDS` variable is commented out or set to `None` in the execution cell.*

### Step 5: Model Evaluation & Benchmark Audit
Run `notebooks/03_model_evaluation.ipynb`.
1. The script loads the generated `llm_extracted_submissions.csv` and merges it with `ground_truth.csv`.
2. It computes strict exact-match accuracy for scalar fields (Revenue, Company Name), Macro F1 scores for list fields (Countries, Requested Coverages), and semantic match accuracy for categorical fields (Industry).
3. It exports `evaluation_metrics.csv` and isolates all mismatched records into `evaluation_errors.csv` for manual human audit. 

## 4. Evaluation Methodology

Because different underwriting fields carry different operational constraints, the evaluation script applies specific metrics to each data type:
* **Strict Exact Match:** Applied to `revenue` and `company_name`. In commercial underwriting, a numeric value or legal entity is either precisely correct or entirely incorrect.
* **Macro Precision, Recall, and F1:** Applied to lists (`countries` and `requested_coverages`). This ensures the model receives proportional credit for capturing a partial list (e.g., extracting two out of three operating territories) rather than recording a binary failure.
* **Semantic Match:** Applied to `industry` to accept valid synonyms and prevent penalisation for semantic equivalents (e.g., "Agriculture" vs. "Farming").

For an in-depth analysis of the benchmark error audit and the architectural design choices, please refer to **`../../docs/Email_Ingestion_Methodology.md`**.
